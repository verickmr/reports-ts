# Memorial Técnico de Desenvolvimento

## 1. Objetivo e escopo

O Portal de Solicitações Internas permite que usuários autenticados registrem demandas, consultem e filtrem solicitações, alterem seu status e acompanhem quantidades por status. O projeto foi desenvolvido como um monorepositório com interface web, API, contratos compartilhados e banco SQL. O foco foi entregar os requisitos funcionais do mini-projeto com regras explícitas e código que possa ser lido e alterado por outra pessoa.

O login obrigatório usa usuário e senha. A API também oferece login Google opcional por OpenID Connect: inicia a autorização, valida o retorno e cria uma sessão local. A interface mostra o botão desse fluxo quando a API confirma que as credenciais OAuth estão configuradas.

Os testes do fluxo Google não exigem credenciais reais.

## 3. Arquitetura e organização das camadas

- `apps/web`: páginas React protegidas por `RequireAuth`, componentes de formulário e status, cliente HTTP e preferência de interface. O estado remoto fica no TanStack Query; Zustand guarda somente estado de apresentação.
- `apps/api`: controladores HTTP recebem e validam entradas, serviços aplicam as regras e usam `PrismaService` para persistência. `SessionGuard` bloqueia as rotas de categorias e solicitações sem sessão válida.
- `packages/contracts`: esquemas Zod e tipos para os formatos trocados entre API e interface. A validação no servidor continua obrigatória, mesmo que o formulário também valide os dados.
- `apps/api/prisma`: schema, migrations e seed. O [dicionário de dados](data-dictionary.md) detalha tabelas, colunas, relações e índices.

O fluxo principal é: a página envia HTTP para `/api`; o controlador valida o corpo, filtros ou código; o serviço executa a regra e consulta o banco pelo Prisma; o controlador devolve o resultado ou um erro HTTP. Em desenvolvimento, o Vite encaminha `/api` para o NestJS. A interface interpreta `401`, `404`, `409` e falhas gerais para mostrar mensagens compreensíveis. O contrato Zod verifica respostas recebidas antes de usá-las na tela.

A separação controlador–serviço–persistência segue o princípio de responsabilidade única: transporte HTTP, regra de negócio e acesso a dados ficam em locais distintos. Componentes React reutilizam campos de formulário e apresentação de status. Não foi criada uma hierarquia de interfaces ou repositórios abstratos sem necessidade concreta; a injeção de `PrismaService` já delimita a dependência de persistência para o tamanho atual do projeto.

## 4. Modelagem e regras de negócio

`users` e `categories` se relacionam com `requests` por chaves estrangeiras. Cada solicitação recebe código sequencial, solicitante da sessão, data de criação e status inicial `OPEN` no servidor/banco. O usuário informa título, descrição e categoria. A categoria deve existir. A edição e a exclusão usam operações condicionadas ao status `OPEN`, evitando alterar ou remover uma solicitação que mudou de estado entre a leitura e a gravação. Falta de registro retorna `404`; estado incompatível retorna `409`.

Os status são `OPEN`, `IN_PROGRESS` e `COMPLETED`. O enunciado não define uma ordem obrigatória de transição; a API aceita qualquer um dos três ao alterar o status. Os filtros cobrem título, categoria, status e período de abertura. Datas são armazenadas com fuso no PostgreSQL; o navegador converte os dias escolhidos para limites ISO de início inclusivo e fim exclusivo. O dashboard agrega as contagens no banco por status e inclui zero para estados sem registros.

## 5. Autenticação e comunicação

O seed cria usuários de demonstração; as senhas vêm de variáveis de ambiente e são armazenadas como hashes Argon2id. No login, a API remove sessões vencidas, cria um token aleatório, persiste somente seu hash e envia o token em cookie `HttpOnly`, `SameSite=Strict`, restrito a `/api`, com validade de oito horas e `Secure` em produção. A cada pedido protegido, o guarda procura a sessão e verifica expiração; logout a remove do banco e expira o cookie. A interface consulta `/api/auth/me` para decidir se pode mostrar as rotas protegidas, mas a autorização efetiva é feita pela API.

O campo `role` já existe no usuário, porém ainda não limita operações: qualquer usuário autenticado pode consultar e alterar solicitações. Isso corresponde à regra expressa no enunciado, que exige autenticação mas não define permissões diferentes por papel. O login Google opcional usa `google_sub` para identificar contas, `google_auth_attempts` para controlar `state`, PKCE e `nonce`, e `jose` para verificar o ID token. Ele cria um solicitante no primeiro acesso e reutiliza a conta nos seguintes, sem associar pelo e-mail uma conta local preexistente. As rotas OAuth estão ativas apenas quando as três variáveis Google são configuradas; o login por senha não depende delas.

## 6. Verificação e análise crítica

Foram executados compilação TypeScript, lint, formatação e build da interface durante o desenvolvimento. O pacote de contratos tem testes automatizados versionados para validação de entradas, filtros, códigos, status e resumo. Há também testes versionados da autenticação Google, inclusive por HTTP, e um teste HTTP para login por senha, sessão, criação, filtros, edição, exclusão, status e dashboard. Localmente, verifiquei as rotas Google e o fluxo obrigatório com PGlite, um banco PostgreSQL compatível em memória. Os iniciadores locais ficaram fora do repositório; o workflow de CI provisiona PostgreSQL 16, aplica as migrations, executa o seed e roda os testes HTTP versionados. O workflow ainda precisa ser executado no GitHub após a publicação do repositório.

As principais limitações são: a API oferece uma rota paginada, mas a interface ainda usa a listagem completa; não há trilha de auditoria das mudanças de status; não há recuperação de senha nem políticas de permissão por papel; o login Google ainda não foi validado com credenciais reais; e o Compose executa apenas PostgreSQL. Para produção, eu adicionaria paginação na interface, auditoria, testes de interface e pipeline de implantação, limpeza periódica de sessões mesmo sem novos logins, proteção de login contra tentativas excessivas e uma análise de CSRF adequada ao domínio e à forma de hospedagem escolhidos. Também serviria frontend e API sob HTTPS e validaria o deploy em ambiente semelhante ao de produção.

Essas melhorias foram deixadas fora do escopo funcional obrigatório para manter a entrega pequena e verificável. As credenciais de demonstração devem ser trocadas antes de expor a aplicação fora de um ambiente local.
